### 4. [HIGH / correctness] Reconfiguring an in-cart dish's options silently overwrites the previous line instead of adding a new one

- **Location:** `frontend/src/pages/MarketplaceMenuPage.vue:1503`
- **Problem:** In MarketplaceMenuPage.vue the marketplace cart keys a line item only by `dish.slug` (no composite key), unlike the direct tenant storefront (CategoryPage.vue/DishPage.vue) which keys by `${slug}::${optionSig}`. The suggested fix (composite slug::optionSig key mirroring CategoryPage/DishPage, or pushing a new line when options differ) is a self-contained frontend change consistent with the existing storefront pattern and needs no owner decision, so autonomous_safe holds.

When a customer lands here with no in-app history (fresh tab, or the referrer is outside the SPA), `router.back()` either no-ops (button does nothing — dead end) or navigates the browser away from the app entirely (losing cart/session context), depending on browser history state. The exact same risk is already recognized and guarded elsewhere in this codebase: NotFound.vue's goBack() (frontend/src/pages/NotFound.vue:115-121) explicitly checks `window.history.length > 2` before calling `router.back()`, falling back to a safe in-app route otherwise. DishPage's back button omits that guard.
- **Impact:** A customer who opens a shared/QR dish link and taps the back arrow can get a non-functional button or be bounced out of the ordering flow, with no way back to the menu short of re-navigating manually — a real dead-end on one of the most commonly deep-linked customer pages.
- **Suggested fix:** Reuse the same guard NotFound.vue already has: if `window.history.length > 2` call `router.back()`, else `router.push({ name: 'menu' })` (or the category page). Pure client-side fix, no backend or product decision involved.
- **Verifier:** Verified against the actual code. DishPage.vue:55-61 has a back button whose click handler is `@click="router.back()"` (line 58) with no guard at all — confirmed by grep, the only two matches for router.back/history.length/goBack in the file are the aria-label and the bare click handler. Compare to NotFound.vue:115-121, which the finding cites accurately: `goBack()` checks `window.history.length > 2` before calling `router.back()`, else falls back to `router.push(...)`. DishPage has no equivalent fallback. The route itself, `browse/:category/:dish` (router/index.js:145), is confirmed to exist and is plausibly deep-linked (shared URLs, QR codes) as the finding claims — this is a customer-facing route (`meta: { interface: 'customer' }`).

The core technical claim is correct: an unguarded router.back() on a page reachable via direct deep link can no-op or navigate the user out of the SPA when there's no in-app history. This is a real, present gap and the suggested fix (reuse NotFound.vue's guard pattern) is accurate and low-risk/autonomous-safe as claimed.

I'm downgrading severity from medium to low, however. The blast radius here is much smaller than NotFound.vue's back button: DishPage always renders a persistent top nav/tab bar and cart access (visible customer layout with menu/cart links elsewhere in the page, and RouterLink to cart is right next to this very button at line 64-72), plus a "not found" state with an explicit `RouterLink to name: 'menu'` (line 24) for when dish lookup fails. So even in the worst case (history.length <= 1, e.g. `router.back()` no-ops or exits app), the user is not stranded on a page with zero other way back — there's still a full app shell/nav around it, unlike a true dead-end. It's a real polish/consistency gap worth fixing (and cheap to fix), but the practical impact is closer to "minor navigational inconsistency for a rare deep-link edge case" than a genuine dead-end blocking the ordering flow, especially since customer layouts in SPAs typically retain persistent chrome (header/tab-bar) around routed content.
