### [medium] Customer marketplace cancel skips the row-lock + newly-cancelled guard, so concurrent cancels double-apply the non-idempotent loyalty clawback and stock restock (and never stand the driver down)
- **file:** `backend/accounts/views.py:5460`  | **surface:** consumer  | **category:** double-apply-race
- **Problem:** MarketplaceOrderCancelView.post loads the order with a plain filter().first() (line 5448), checks status != CANCELLED OUTSIDE any lock (line 5454), then enters `with _dbtx.atomic()` (line 5460) and unconditionally runs _refund_wallet_for_cancelled_order, _reverse_loyalty_for_cancelled_order and _restock_cancelled_order (5468-5470). This diverges from the two hardened cancel paths â€” refund_and_cancel_delivery_order (menu/views.py:7814-7833) and OwnerOrderStatusUpdateView (menu/views.py:7925-8067) â€” which BOTH take a select_for_update() lock on the order row and run loyalty-reversal/restock only when THIS call actually flipped the order to CANCELLED, precisely because (per the helper's own docstring) '_reverse_loyalty_for_cancelled_order and _restock_cancelled_order are NOT internally idempotent'. The wallet refund here is safe (credit_wallet is idempotent on cancelrefund:{schema}:{order.id}), but the loyalty clawback and restock are not, and this path has no serialization. It also never calls cancel_delivery_job_for_order, so a cancelled+refunded marketplace delivery order leaves its live DeliveryJob dispatching a driver (the owner path stands the driver down at menu/views.py:8073-8078).
- **Failure:** A customer double-taps Cancel on a PENDING marketplace order (throttle only rate-limits, does not serialize), or the stuck-job auto-refund sweep fires on the same order at the same instant. Both requests read status=PENDING before either commits; each sets CANCELLED and runs _reverse_loyalty_for_cancelled_order, applying delta=(restored-earned) to the customer's loyalty balance TWICE â€” e.g. an order that earned 100 points claws back 200, wiping 100 points the customer earned on other orders (clamped at 0). _restock_cancelled_order also returns the reserved stock twice, inflating stock_qty above the real count and letting the restaurant oversell. Concretely: two concurrent cancels of a PENDING order with points_earned=100, stock_qty of the dish=3 â†’ customer loses 200 loyalty points and the dish's stock_qty becomes 5 for 3 physical units.
- **Fix:** Bring MarketplaceOrderCancelView.post to parity with the two hardened siblings. Inside the atomic() block, re-load the row under a lock and gate the non-idempotent helpers on the transition this call actually performed:

    with _dbtx.atomic():
        locked = _Order.objects.select_for_update().filter(pk=order.pk).first() or order
        newly_cancelled = locked.status != _Order.Status.CANCELLED
        if newly_cancelled:
            locked.status = _Order.Status.CANCELLED
            locked.status_updated_at = _tz.now()
            locked.save(update_fields=["status", "status_updated_at", "updated_at"])
        order = locked
        _refund(order, tenant_id=tenant.id)   # idempotent â€” always safe
        if newly_cancelled:
            _revloy(order)
            _restock(order)

Then, after the transaction (best-effort, mirroring menu/views.py:8073-8078), stand the driver down:
        try:
            from accounts.delivery_service import cancel_delivery_job_for_order
            cancel_delivery_job_for_order(tenant.id, order.order_number)
        except Exception:
            pass

Note _customer_can_cancel is evaluated on the pre-lock read; that is fine because the helpers now run only when THIS call flips the row. Add a regression test that fires two concurrent cancels of a PENDING order and asserts loyalty delta and restock are each applied exactly once (the money-concurrency suite already has the harness, e.g. backend/tests/test_money_concurrency.py).
